#### Problem
Mod developers have wanted to create their own VariantPacks, but are turned off at the idea of using ThunderKit for the full experience (Understandable)

They wish they could utilize any method for creating Variants, while the mod could always be done via code, there is no "recommended" method for creating Variants.

#### Solution
Create a system for making variants outside of thunderkit, ideas include:

* Make the VariantPack an interface such as a VariantPackProvider
    * Make the VariantPack class a C# class instead of a Scrobj
    * Add coroutines for initialization
* Create a "VariantFactory"
    * Requires to have one field (Body/Master name)
    * Have builder-chainable methods for configuring the factory
    * Have a "Clone" method to clone a configuration from one factory to another
    * Have a "Construct" method, that takes the configuration from the Factory and spits out a result
* Idea is, mod developers create factories, factories create VariantDefs, VariantDefs are added to the VariantPack

### Variants do not persist across stages

#### Problem

Monster Variants do not persist across stages, this wasnt a problem prior to some specific implementations regarding CU8.

The biggest example of this being a problem is with the Artifact of Devotion. your Lemurians persist across stages, yet their variants do not. A lemurian egg may spawn a Flamethrower Lemurian, but on the next stage they'll not be Flamethrower

This also applies to the character Chirr from Starstorm 2, players may befriend a powerful variant that stops being powerful on next stage.

#### Solution

Change how Variants are assigned to bodies.

* VariantDef can now specify either a Body or a Master prefab.
    * If the VariantDef specifies a Master, it'll only be added to said master, players could create a VariantDef for LemurianBruiserIceMaster so the variant applies to only the Runald Lemurian Bruiser
    * If the VariantDef specifies a Body, it'll be added to ALL CharacterMaster prefabs that utilize the Body.
    * "bodyName" string is now a custom class that accepts either an AddressReferencedBodyPrefab or an AddressReferencedMasterPrefab
        * Add these two AddressReferencedAssets to R2API.Addressables
* Variant systems now specifically utilize Masters over Bodies    
* VariantProviders are now _master bounded_
* When the master is spawned, it requests what VariantDefs to utilize
    * After the Body spawns, it queries the Masters's Defs to get the chosen Variants.
    * Variant application proceeds as usual.
* Figure out VariantSummon to utilize masters instead
* PlayerCharacterMaster variants work different:
    * If the player spawns as a FlameThrower lemurian, it should keep the Variants across stages
    * Body prefab changing flushes what VariantDefs it has
    * Make a config so the Variants are different each time the body spawns, or if the variants should be flushed on moving to the next stage

### Project Health

#### Problem
VarianceAPI has been written prior to MSU 2.0, it has a lot of codesmell from bad desicions taken during its development.

Offenders include:
* Poor project structure, couple of assets being duplicated
* Networking extensions not on their respective catalogs
* Potentially poor ILHook matching
* Enums on unity editor serialization contexts (vomit inducing)
* Difficult to work token replacements
* Poor command experience for spawning or becoming variants
* ContentPack wannabe but with a Scrobj
* Not utilizing DropTables for variant rewards
* VariantVisuals being pre-memopt

#### Solution

* Make sure things are not duplicated
* Add networking extensions to their own catalog (VariantIndex to VariantCatalog, VariantPackIndex to VariantPack system)
* Rewrite ILHook matching to break less, ask for help for this
* Stop using enums on Editor facing scripts. maybe utilize Scrobjs as Enums (?)
* Make token replacements utilize string formatting. ``Flamethrower {0}``. Avoiding formatting numbers should allow for full replacements
* Utilize the ":" format for optional arguments on commands. ``vapi_spawn_ai LemurianMaster variants:Flamethrower,Badass eliteType:xyz, count:1``
* Make the VariantPack not be a ScriptableObject, have it initialize like an actual ContentPack
* Keep the percentage based drops, but allow for DropTables for custom rewards
* Make VariantVisuals utilize the TransformPath from MSU, no indices since they're no longer reliable
